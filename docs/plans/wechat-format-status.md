# 改动计划:微信消息格式与状态反馈

状态:已完成(2026-10-06 实施并通过真机复测;实施中发现并修复了事件循环线程自投递的死锁,状态通知改为由服务线程排水)。

已确认的决策(2026-10-06):id 全局改、冲突秒数 +1 重试、保留 subject 行、反馈措辞保留原文案、逾期补发反馈、接受"失败无法经微信反馈"的限制、增加无法归属反馈、ask 脚注精简(改动 5,提示文案定为"当前有多条消息等待回复，请使用引用回复")。实施中的两处补充:并发标志仅对 ask 计算与传递;"无法归属"反馈只在确有等待中的 ask 或真歧义时发送,无关闲聊不提醒。

## 改动 1:截止时间显示化简

位置:`gateway/wechat.py` `_send` 中的 `回复截止:` 行。

新增纯函数(便于单测),输入 `deadline_at`(ISO,UTC),输出北京时间文案:

- 缺失 → `以记录页面为准`(现状回退不变);
- 与**发送时刻**(北京时间)同一天 → `今天 HH:MM:SS`;
- 次日 → `明天 HH:MM:SS`;
- 更晚 → `M月D日 HH:MM:SS`(如 `10月9日 14:00:00`)。

规则:固定 UTC+8(无夏令时);"今天/明天"按发送时刻计算,接受跨零点阅读时的语义漂移;秒级精度、两位补零。仅微信通道,邮件不动。

## 改动 2:请求编号改为 YYYYMMDDHHmmss

位置:`gateway/store.py` 请求创建处(现为 `uuid4().hex`)。

- 生成北京时间 `YYYYMMDDHHmmss`(14 位纯数字,字典序=时间序);
- **同秒冲突**:主键冲突时秒数 +1 重试(上限若干次),保持纯 14 位,时间戳最多偏差数秒;
- **全局生效**:邮件主题 `[AC:id]`、合成 Message-ID(`<ac.{id}@agentcall.local>`)同步变短;
- 存量 uuid 编号记录不做迁移,token 正则(`[A-Za-z0-9_-]+`)对两种格式天然兼容,新旧共存期匹配不受影响;
- 北京时区常量如被改动 1 复用,统一定义一处。

## 改动 3:消息头部

位置:`gateway/wechat.py` `_send` 首行。

```
旧:agentCall · {agent_name}
新:{agent_name} · Request   (kind == ask)
   {agent_name} · Notice    (kind == notify)
```

- `agent_name` 缺失回退 `Agent · Request/Notice`;
- 第二行 subject 保留(已确认);
- Notice/Request 用英文(已确认)。

## 改动 4:状态经微信反馈给用户

触发与文案(全部纯一行、**不带** `[AC:编号]`):

| 事件 | 文案 | 说明 |
|---|---|---|
| ask 收到首条按时回复(waiting→replied) | `{agent_name} 已读` | 触发时机=回复到达,非真实已读(用户确认采用原措辞) |
| ask 超时(timed_out) | `{agent_name} 不再等待你的回复` | 挂在超时清扫处 |
| 迟到回复归档(每条) | `回复已记录（已逾期）` | 已确认补发,避免用户等"已读"落空 |
| 目标联系人回复无法归属(AMBIGUOUS/UNMATCHED) | `无法确定你的回复对应哪个问题，请引用对应消息回复，或在回复中带上 [AC:编号]` | 已确认新增;此前只存诊断用户不可见 |

不发反馈的场景(已确认):notify 类消息;发送失败/结果未知(微信通道彼时不可用,靠邮件回退与前端);已 replied 记录的后续追加回复(只反馈一次,避免刷屏)。

实现要点:

- store 层只负责**返回结构化结果**(状态翻转/迟到归档/无法归属原因),发送由 service 层完成,store 不持有发送能力;
- 新增轻量发送路径(复用现有连接与登录校验,不建 record、不写状态、不重试;发送失败仅记诊断);
- 反馈消息为账号自发消息,echo 被 `is_self` 过滤,无递归风险;不带编号则用户引用反馈消息回复时走裸文本规则,不产生误归属;
- 高效模式与经典模式同一触发点(状态翻转在 `add_reply`,与领取无关)。

## 改动 5:ask 脚注精简与并发引用提示

位置:`gateway/wechat.py` `_send` 脚注,与改动 1/3 同一段组包逻辑。合并后的 ask 最终形态:

```
Claude · Request
部署前确认

请确认是否立即部署到生产环境。

[AC:20261006215233]
回复截止：今天 21:57:33
```

- 删除现有两处提示文字:整句"请直接回复;同时存在多个问题时,请在回复中保留上面的 [AC:…] 标识。"与"逾期回复仍会记录,但不会作为本次等待的及时决策。"(逾期语义由改动 4 的逾期反馈承接);
- 脚注仅保留 `[AC:编号]` 与 `回复截止:` 两行(截止缺失时沿用"以记录页面为准"回退);
- **发送时同一账号+联系人还有其他 waiting/sending 的 ask**(不含本条)→ 追加一行:`当前还有其他问题在等待，请长按引用这条消息回复`;
- notify 脚注维持现状:仅 `[AC:编号]`,无截止、无提示。

实现要点:

- store 新增查询:同 `wechat_account_id`+`target_contact_id`、kind=ask、status∈(waiting,sending)、排除本条 id 的计数(不限 30 天窗口,stuck 的 sending 不应漏计);
- service 发送路径查询后把标志传给网关发送(`send(record, …)` 加参数,transport 不持有 store);`tests/test_channels.py` 的 FakeWechat 同步改签名;
- 时序效应(接受):两条排队 ask 先后发送,第一条发出时无并发、不带提示,第二条带;并发期间裸文本回复仍按歧义拒绝,由改动 4 的"无法归属"反馈引导改用引用。

## 测试

- `_format_deadline`:今天/明天/后天、北京零点边界(UTC 16:00)、缺失回退;
- 编号生成:同秒两条 → 均为 14 位纯数字且互异;旧 uuid 记录仍可匹配;
- 头部:ask/notify/无名回退三种;
- 反馈:按时回复触发一次且仅一次、超时触发、迟到触发、无法归属触发、notify 不触发、追加回复不触发、文案不含 `[AC:`;
- 脚注:无并发 ask 时无引用提示行、有并发时有;notify 脚注仅编号;并发计数排除自身、仅计同账号+联系人的 waiting/sending;
- 组包快照:整条消息文本(头部/subject/正文/编号/截止行/条件提示行)符合新格式。
